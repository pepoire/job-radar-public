# 案件レーダー（job-radar）

フリーランス案件を毎日集めて、**自分の経歴と希望条件で採点し直す**ツール。
自作のレコメンダーで、案件の一覧・ステータス管理・応募文の下書きまでを1つの画面に入れている。

作った動機は「プラットフォームの自動レコメンドが的外れだった」こと。
通知経路を増やすのではなく、**ランキングを自分の条件でやり直す**のが目的。
案件のプールは同じものを見ていて、並べ替えだけを自分でやる。

> 案件の取得は `JobProvider` の差し替えで行う設計です。
> このリポジトリには `fixtures/demo.json`（サンプルデータ）を読む provider が入っているので、
> 何も設定せずに画面と採点を動かせます。

---

## 何が入っているか

```
取得（provider）→ ハードフィルタ → LLM採点 → 保存 → 通知 / 画面
```

| 層 | 中身 |
|---|---|
| **取得** | `JobProvider` の契約だけ。実装は fixtures を読む `ExampleProvider` のみ |
| **判断** | ハードフィルタ（機械的に落とす）→ LLM採点（構造化出力） |
| **採点** | `lib/scoring.ts`。**％の計算はここだけ**にあり、LLM に点数を言わせない |
| **画面** | 一覧 / ステータス別ボード / 担当者提案（応募文の下書きと送信依頼） |
| **日程** | Googleカレンダー（iCal 非公開URL）の空きから商談候補を出す |

## 設計で気をつけたこと

### 1. LLM に点数を言わせない

LLM が返すのは**数えられることだけ**にしている。

- 必須要件の総数と、そのうち満たしている数
- 絶対条件（リモート・契約形態・職種）に反しているか
- ドメイン経験があるか、案件票がドメイン経験を求めているか
- AI がプロダクトの中核か

重み付けと計算は `lib/scoring.ts` に置いてある。だから「なぜこの数字か」を人に説明できる。
画面では掛けた途中の値を並べて出すので、70%の内訳をそのまま追える。

```
必須要件の充足  5 / 5 件を満たす   ×1.00   100%
ドメイン経験    案件票は求めていない ×0.95    95%
競合の多さ      担当者が選んだ提案   ×1.00    95%
```

**この数字は確率ではない。** 並べ替えと閾値のための指標として扱っている。

### 2. 「希望に合うか」と「自分が通りそうか」を分ける

```
総合マッチ度 = 希望適合度 × 通過可能性
```

掛けるのは、片方が低ければ応募する意味がないから。
「欲しいが通らない」も「通るが欲しくない」も価値は低い。
加重平均にすると片方の低さが隠れるので積にしている。

### 3. 取得できなかったことを「0件」に丸めない

`FetchResult.status` に `no_data`（公開されていない）と `failed`（壊れた）を必ず分けて持つ。
これを混ぜると、サイトの作りが変わって取れなくなった日に
**「今日は新着なしです」と報告し続ける**という一番危ない壊れ方をする。

同じ理由で、LLM の採点に失敗した案件も黙って捨てずに「採点できず」として残す。

### 4. 数字が嘘にならないようにする

実装中に踏んだものを、そのままテストとして固定してある。

| 事故 | どう直したか |
|---|---|
| 時間単価 5,680円/時 を月額5,680円として読み、約91万円の案件を捨てた | 月額と時間単価を別のフィールドで持ち、比較のときだけ換算する |
| 必須要件が1項目だけの案件票が満点を取り、5項目すべて満たした案件と並んだ | 件数が少ないほど「判断できない側」に寄せる（満点には届かない） |
| 「未経験の業界」で85%の案件に一律 ×0.70 がかかり、順位に寄与していなかった | 案件票がドメイン経験を**求めているときだけ**効かせる |
| 応募文の ○× が、満たしていない経験に ○ を付けた | 箇条書きの折り返しを1項目として扱い、不足要件を項目に1対1で割り当てる。割り当てられなければ下書きを作らない |

詳しくは `docs/SCORING.md`。

### 5. 媒体名を採点とUIに書かない

provider は「経路」を申告する。

| 経路 | 意味 |
|---|---|
| `web` | 公開されていて誰でも応募できる |
| `mail` | 担当者が個別に送ってきたメール |
| `agent` | 担当者が経歴を見て選んだ提案 |

採点で効くのは「誰でも見られるものか、人が選んだものか」だけで、どの媒体かは関係がない。
媒体が増えても `scoring.ts` と画面に手を入れなくてよい。

## 動かす

```bash
pnpm install
cp criteria.example.json criteria.json
cp criteria.example.md   criteria.md
cp career.example.md     career.md
# 3つを自分の条件・経歴に書き換える

pnpm radar preview --no-llm   # 取得とハードフィルタまで（LLM を呼ばない）
pnpm radar preview            # 採点まで
```

**APIキーは無くても動く。** 既定では手元の [Claude Code](https://claude.com/claude-code) CLI を
`claude -p --output-format json --json-schema` で呼んで構造化出力を受け取る。
`OPENAI_API_KEY` か `ANTHROPIC_API_KEY` を入れればそちらも使える
（`JOBRADAR_LLM_ORDER` で順番を変えられる）。

画面も見る場合:

```bash
pnpm local      # ローカルDBを立てて dev サーバーを起動
pnpm radar preview --persist   # 採点結果をDBに入れる
```

> Prisma のスキーマを変えたら **dev サーバーを再起動する**。
> 起動中のプロセスが古い Prisma クライアントを掴んだままになり、
> 「カラムが存在しない」で落ちる。

## 自分の provider を足す

`JobProvider` を1つ実装して `buildProviders()` に並べるだけ。
そこから先（ハードフィルタ・採点・保存・通知・画面）は媒体を知らないので触らなくてよい。

```ts
export class MyProvider implements JobProvider {
  readonly name = "my-source";

  async fetch(seenUids: ReadonlySet<string>): Promise<FetchResult> {
    // 取れた -> { status: "ok", jobs, checked, sources }
    // 公開されていない -> { status: "no_data", ... }
    // 壊れた -> { status: "failed", error: "...", ... }   ← 0件に丸めない
  }
}
```

`src/lib/providers/example.ts` が最小の実装例。

## 技術スタック

Next.js 14（App Router）/ React 18 / TypeScript / TanStack Query / Tailwind CSS /
Prisma + PostgreSQL / zod（LLM の構造化出力スキーマ） / Vitest

DBは任意。`DATABASE_URL` が無ければファイル（`state/`）に保存して動く。
