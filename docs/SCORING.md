# 案件レーダーの採点の仕組み

人に説明するための資料。「なぜこの案件が37%なのか」を answerable にすることが目的。

---

![案件レーダーの仕組み](images/flow.png)

## 1. 何をしているか

毎朝1回、案件を集めて **総合マッチ度** を出し、高いものだけ通知する。

```
総合マッチ度 ＝ 希望適合度 × 通過可能性
```

2つの軸を分けて持ち、掛け合わせる。

| 軸 | 問い |
|---|---|
| **希望適合度** | この案件は自分が**欲しい**ものか |
| **通過可能性** | 自分がこの案件に**通りそう**か |

### なぜ掛けるのか

片方が低ければ応募する意味がないから。「欲しいが通らない」も「通るが欲しくない」も、
応募する価値は低い。**加重平均にすると片方の低さが隠れる**ので積にしている。

例:

| 案件 | 希望適合 | 通過可能性 | 総合 |
|---|---|---|---|
| フルリモート・週3・目標単価超・開発が主 | 100% | 28% | **28%** |
| 一部リモート・週5・目標単価超・生成AI | 43% | 72% | **31%** |

上の案件は**希望には100%合っている**（条件が理想的）が、必須要件が1/3しか満たせないので
総合が28%に落ちる。5点満点の採点だったときは、これが「4点」で上位に出ていた。

## 2. パーセンテージの作り方（ここが肝）

### AIに「78%」と言わせない

LLMが出す数字はキャリブレーションされていない。「78%」と言わせても根拠がなく、
なぜその数字かを説明できない。なので**役割を分けている**。

| | 担当 |
|---|---|
| **AI（LLM）** | **数えること**と**書いてあるかの判定**だけ |
| **コード** | 重み付けと計算（`src/lib/scoring.ts`） |

AIが出すのはこれだけ。

- 案件票の必須要件は**何項目あるか**、そのうち**何項目満たしているか**
- 絶対条件（フルリモート / 業務委託 / 開発主体）に**反しているか**
- そのドメイン（業界）の経験が**あるか**
- AIがプロダクトの**中核か、活用レベルか、無いか**
- 案件票から読めるリモート度、月額、重なる技術

**パーセンテージは一切AIに出させていない。** だから計算式を見せれば誰でも同じ数字を再現できる。

### この数字は確率ではない

「37%なら37%の確率で受かる」という意味ではない。
**並べ替えと閾値のための指標**である。そう説明する。

## 3. 希望適合度の計算

基準を100として、条件に応じて掛けたり足したりする。

### 掛ける（条件を満たしていないほど下がる）

| 項目 | 係数 | 理由 |
|---|---|---|
| 絶対条件に違反 | **×0.35** | フルリモートでない / 正社員化の示唆 / 開発が主でない |
| 単価が目標（`targetMonthlyJpy`）以上 | ×1.00 | |
| 単価が下限（`minMonthlyJpy`）以上・目標未満 | ×0.85 | |
| 単価が下限未満 | ×0.50 | |
| 単価の記載なし | ×0.75 | 非公開案件に高いものが混ざるので落としきらない |
| 主軸の技術が一致（`scoring.ts` の `CORE_STACK`） | ×1.00 | |
| 周辺の技術のみ一致 | ×0.80 | |
| 重なる技術が無い | ×0.55 | |

**絶対条件の違反を0にしない**のは、出社頻度や条件次第で検討の余地が残るから。
「見えなくする」のではなく「下に沈める」扱いにしている。

### 足す（上振れの余地）

| 項目 | 加点 |
|---|---|
| AIがプロダクトの中核 | +10 |
| PM実績として職務経歴書に書ける | +5 |
| 週4日以下（休みが取りやすい） | +5 |

精算条件（精算基準時間 140〜180h など）は**点数に入れていない**。
業界の標準的な書き方で、記載があること自体は不利ではないため。
加点にすると「精算なし」の案件だけが得をして、普通の案件が相対的に損をする。
画面には数字だけ事実として出す。

## 4. 通過可能性の計算

**必須要件の充足率**を軸に、書類で効く要素で調整する。

| 項目 | 係数 |
|---|---|
| 必須要件の充足率 | **0.2 + 0.8 × (満たした数 / 総数)** |
| 必須要件の記載が無い | 0.60（判断できないため） |
| ドメイン経験あり | ×1.00 |
| 案件票がドメイン経験を求めており、近い業界の経験がある | ×0.95 |
| 案件票がドメイン経験を求めているが未経験の業界 | ×0.85 |
| 案件票はドメイン経験を求めていない（近い業界の経験） | ×1.00 |
| 案件票はドメイン経験を求めていない（未経験の業界） | ×0.95 |
| 担当者が選んだもの（個別メール / プラットフォームの提案） | ×1.00 |
| 公開案件（誰でも応募できる） | ×0.85 |
| 商談1回 | ×1.00 |
| 商談2回 | ×0.95 |
| 商談3回以上 | ×0.85 |

### 自主開発をどう数えるか

収益化していない自主開発でも、**技術そのものを問う要件には数える**。
「TypeScriptを用いた開発経験」は、書いたコードが動いていれば商用かどうかに関係がない。

**年数が指定された要件（「実務経験5年以上」など）には数えない。**
エージェントの書類審査では実務年数として扱われないので、数えると数字が嘘になる。
ドメイン経験が自主開発だけの場合も HAVE にはせず PARTIAL までにする。

### ドメイン経験は、案件票が求めているときだけ効かせる

最初は「未経験の業界 ×0.70」を一律でかけていた。手元の実データで数えて直した。

- 必須スキルが取れている **75件のうち、ドメイン経験に言及しているのは9件（12%）**
- 言及しているのは SAP・財務会計・製造・医療画像といった、業務知識そのものが仕事の領域
- それにもかかわらず、採点済み40件のうち **34件（85%）が「未経験の業界」判定**

**85%にかかる係数は順位を付けない。全体を3割下げるだけ。**
しかも案件票がドメイン経験を求めている場合、それは必須要件の1項目として
書かれているので「必須要件の充足」にすでに数えられている。
そこへ係数でも引くと、同じことを二重に引くことになる。

そのため、

- 案件票がドメイン知識を**スキル要件として**求めているか（`domainRequired`）をLLMに判定させる
- 求めていなければほぼ引かない（×0.95）
- 求めているときも、必須要件との二重計上を避けて控えめに引く（×0.85）

業界欄に業界名が書かれているだけ、案件名に業界が入っているだけでは
「求めている」とはみなさない。

### 記載が少ない案件票に満点を出さない

最初は充足率をそのまま使っていた。その結果こうなった。

| 案件 | 必須要件 | 通過可能性 |
|---|---|---|
| オープンポジション（業務内容も「TypeScriptを用いた開発支援」だけ） | 1 / 1 | 100% |
| 生成AIツール開発（3項目すべて満たす） | 3 / 3 | 100% |

**記載が薄い案件票ほど満点を取りやすい。** 数えられるほど不利という逆向きの構造だった。
そこで架空の観測を2件ぶん足して、件数が少ないほど「判断できない側（0.5）」に寄せる。

| 充足 | そのままの比率 | 寄せたあと |
|---|---|---|
| 1 / 1 | 1.00 | 0.67 |
| 3 / 3 | 1.00 | 0.80 |
| 5 / 5 | 1.00 | 0.86 |
| 4 / 5 | 0.80 | 0.71 |

満点（1.00）には決して届かない。案件票を全部満たしていても「通る」と言い切れるもの
ではないので、それが正しい。

**抑えるのは上振れだけ。** 「不足している要件が挙がっている」のは観測された事実で、
件数が少なくても不確かではない（経歴に無い要件が具体的に1つある）。
一方「全部満たしている」は不足が観測されなかっただけで、記載が薄い案件票では
何も言っていないのと同じ。そのため 0/2 のような案件は素直に低いままにする。

### 必須要件0でも0%にしない

充足率をそのまま掛けると 0/3 で通過可能性が0%になるが、それは
**「応募しても絶対に通らない」という意味**になってしまう。
必須要件を満たしていなくても書類で見てもらえる可能性はゼロではないので、
下限0.2を置いて 0.2〜1.0 の幅にしている。

### 画面で計算を追える

「なぜ70%なのか」は、不足している必須要件（画面の赤い行）だけでは説明にならない。
必須要件を5/5すべて満たしていても70%になる案件がある。落ちている30%は
ドメイン経験の係数（未経験の業界 ×0.70）だからで、赤い行には何も出ない。

そのため各案件のカードに内訳を出している。掛けた「途中の値」を順に並べる形で、

| | | | |
|---|---|---|---|
| 必須要件の充足 | 5 / 5 件を満たす | ×1.00 | 100% |
| ドメイン経験 | 未経験の業界 | ×0.70 | 70% |
| 競合の多さ | 担当者が選んだ提案 | ×1.00 | 70% |
| 商談回数 | 1回 | ×1.00 | 70% |

「何%分がどの要因か」という割り当ては作っていない。掛け算なので、
各要因に点数を配分すると嘘になる。走っている値をそのまま見せる。

### 1.0を超える係数を置かない

「担当者メールは加点」ではなく「公開案件を0.85に減点」という形にしている。
1.0超の係数を置くと上限100%に張り付いて、内訳が読めなくなるため。

## 5. 通知の閾値

| 総合 | 扱い |
|---|---|
| 60%以上 | 応募すべき |
| 40%以上 | 検討に値する |
| 40%未満 | 低マッチ（通知しないが、画面には残る） |

Slackに出すのは40%以上だけ。**それ未満もデータベースには残り、画面から見られる。**
条件をチューニングするには「なぜ落ちたか」を見る必要があるため。

## 6. 採点する前に機械的に落としているもの

LLMを呼ぶ前にハードフィルタを通す。ここで落ちた理由は必ず言語化して残す。

| 条件 | |
|---|---|
| NG職種 | PMO / ヘルプデスク / 運用監視 / COBOL / SAP など。**タイトルだけでなく必須スキル欄も見る** |
| 常駐と明記 | 落とす |
| 単価が下限未満 | 週4日以下の案件は下限を緩める（時間単価で見れば高いため） |
| 単価の記載なし | **落とさない**（非公開案件に高いものが混ざる） |

これでLLMの呼び出し数を抑えている（1回の実行で最大25件）。

## 7. 設計上の約束

説明するときに一番大事なのはここ。

### 取得失敗を「新着ゼロ」にしない

サイトのHTMLが変わって0件になったのに、静かに「今日は新着なしです」と報告し続けるのが
一番危ない壊れ方。なので取得結果を4状態に分けている。

| 状態 | 意味 |
|---|---|
| `ok` | 取得成功（0件でも接続とパースは成功している） |
| `no_data` | 接続はできたが対象が公開されていない |
| `failed` | ネットワーク/パース失敗（**仕様変更の疑い**） |
| `not_configured` | 認証情報が未設定 |

`failed` はSlack本文の一番上に出し、APIも200ではなく207を返す。
一覧から1件もIDが取れない、新規IDの詳細を1件もパースできない、といった状況は成功扱いにしない。

### 推測で埋めない

単価が書かれていない案件を「高そう」と採点しない。データの欄も0や空文字で埋めず未設定のまま残す。
プロンプトにも「書かれていないことは記載なしとして扱う」と明記し、`zod` で構造化出力を検証してから下流に流す。

### 単位を混同しない

月額と時間単価を**別のフィールド**で持つ。比較は「時間単価×160h」の換算値で行い、
**換算値であることを表示から消さない**（「時間単価5,680円（月160hで約91万円）」）。

> 実際に踏んだバグ。`単価：5,680／時` を単位を見ずに拾って月額5,680円として扱い、
> **月額換算で約91万円の案件を「1万円」として捨てていた。**

### フラグを信じない

「リモートワーク：可」はフルリモートを意味しない。

> 実データにあった案件: 案件情報欄が「リモートワーク：可」なのに、
> 担当者コメントが「**基本常駐での作業となります**」。同じ案件票の中で矛盾していた。

なのでフラグではなく本文を読ませ、断定できなければ「判断できない」として扱う。

### 通知しなかったものも残す

スコアが低かったもの、ハードフィルタで落ちたもの、採点に失敗したものも
すべてデータベースに残り、画面のタブから理由つきで見られる。

## 8. チューニングのしかた

的外れなものが届いたら、この順で直す。

| 症状 | 直す場所 |
|---|---|
| 職種が違う | `criteria.json` の `ngTitleKeywords` に足す |
| 探す範囲を変えたい | `criteria.json` の `searches`（provider が解釈する） |
| 評価の観点が違う | `criteria.md`（LLMが読む希望条件の文章） |
| 経歴の見落とし | `career.md`（**ここに無い経験は評価に反映されない**） |
| 通知が多い / 少ない | `criteria.json` の `notifyTotalMin` |

計算の内訳（どの係数がいくつ効いたか）はデータベースに保存しているので、
「なぜこの数字か」は後から辿れる。
